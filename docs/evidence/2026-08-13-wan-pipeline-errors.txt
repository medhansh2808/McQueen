1. SSH password prompt fails in non-interactive agent shell
--------------------------------------------------------------------------------
SYMPTOM:    ssh from the agent shell prints "ssh_askpass: exec(/usr/bin/
            ssh-askpass): No such file or directory" then "Permission denied".
ROOT CAUSE: The agent terminal has no TTY (stdin is not a terminal) and
            DISPLAY is set but no ssh-askpass helper exists. SSH cannot prompt
            for a password non-interactively.
RESOLUTION: Use a transient askpass helper: write a small script that echoes
            the password, chmod 700, run with SSH_ASKPASS + SSH_ASKPASS_
            REQUIRE=force under setsid, delete the helper afterwards. Password
            is never written to the repo and the helper is removed after use.
STATUS:     RESOLVED (workaround; native interactive SSH still requires the
            human to run commands in their own terminal)

--------------------------------------------------------------------------------
2. SSH command hangs / times out when starting background processes
--------------------------------------------------------------------------------
SYMPTOM:    ssh that launches a nohup background process and then echoes
            output times out ("Command timed out"). The process IS started.
ROOT CAUSE: ssh keeps the channel open while the backgrounded process holds
            stdout/stderr fds, so the command never returns.
RESOLUTION: Start the process in one ssh call (quick return), then verify
            state with a separate ssh call. Do not chain verification into the
            same command that backgrounds a process.
STATUS:     RESOLVED (operational pattern)

6. WebRTC ICE FAILED — Jetson gathers zero srflx candidates (THE BIG ONE)
--------------------------------------------------------------------------------
SYMPTOM:    WebRTC video never connected over the WAN. RTX receiver showed
            "ICE ... FAILED"; Jetson sender stuck in CHECKING forever.
ROOT CAUSE: Jetson GStreamer 1.14.5 + libnice 0.1.14 webrtcbin gathers only
            "host" candidates and ZERO "srflx" (server-reflexive) candidates
            even with stun-server property set. Without a srflx candidate the
            Jetson advertises only its private 10.147.x (CGNAT) address, which
            the RTX cannot reach. RTX (GStreamer 1.20.3 + libnice 0.1.18)
            gathers srflx fine. This is a GStreamer-version limitation, not a
            network/config problem.
EVIDENCE:   Raw STUN from the Jetson WORKS (UDP binding request -> mapped
            address 152.58.1.190 in 69ms). So the network is fine; the old
            webrtcbin simply does not turn STUN into srflx candidates.
RESOLUTION: Abandon WebRTC for video. Use raw RTP-over-UDP over the SAME
            manual STUN + broker rendezvous NAT-punch pattern that already
            proved 60/60 ACKs at p50 43.1ms for control (tools/realtime/
            direct_udp_peer.py). New scripts: tools/realtime/gst_jetson_rtp_
            wan.py (sender) + tools/realtime/gst_rtx_rtp_receiver.py.
STATUS:     WORKAROUND DEPLOYED; WebRTC remains BROKEN on Jetson's stack.
            A future fix could be: newer GStreamer/libnice on the Jetson,
            or a TURN relay. Neither needed for the <100ms proof (see #8).

9. Sender bug: one capture entry consumed per RTP packet instead of per frame
--------------------------------------------------------------------------------
SYMPTOM:    (found during code review before deployment) — the rtph264pay pad
            probe popped one (frame_id, capture_mono_ns) from the capture
            queue for EVERY RTP packet, but each frame produces multiple RTP
            packets, so frame metadata would have been misaligned.
ROOT CAUSE: Probes fire per-packet; the code assumed per-frame.
RESOLUTION: Detect frame boundaries by RTP timestamp change; consume exactly
            one capture entry per new timestamp. Verified by unit test
            tools/realtime/test_rtp_association.py (5 frames, exact order).
STATUS:     RESOLVED (pre-deployment catch)

10. Rendezvous announce window too short (late-starting peer never learns)
--------------------------------------------------------------------------------
SYMPTOM:    Sender started AFTER the receiver's 8-second announce window
            expired -> "RTX UDP candidate missing after repeated
            announcements".
ROOT CAUSE: Both sides only announced their UDP candidate for 8 seconds at
            startup. If a peer connects late, it never receives the address.
RESOLUTION: Announce continuously for the whole run (thread loops every
            0.35s until stop), and wait for the peer up to 60s.
STATUS:     RESOLVED (both scripts updated, redeployed)

16. Sender crashed right after NVENC init (use-after-free in RTP probe)
--------------------------------------------------------------------------------
SYMPTOM:    gst_jetson_rtp_wan.py reached NVENC init ("===== NVMEDIA: NVENC
            =====" in log) then the process died. No traceback in log.
ROOT CAUSE: The rtph264pay pad probe read mapinfo.data and then used that
            bytes object AFTER calling buf.unmap(). On the Jetson's old
            GStreamer 1.14 / PyGObject stack this is a use-after-free that
            crashes the process around the first encoded frame. (The RTX,
            on GStreamer 1.20/PyGObject 3.42, tolerates it — which is why
            the laptop test and RTX-side code never crashed.)
RESOLUTION: Copy payload with bytes(mapinfo.data) while the buffer is still
            mapped, before unmap(). Also wrapped both pad probes in
            try/except that logs to /tmp/mcq_sender_probe_errors.log and
            returns OK instead of letting an exception kill the process.
STATUS:     FIXED (deployed to Jetson on next restart)

20. Sender probe NameError flood: `% 30 < n` with undefined `n` (FOUND in
    pulled evidence, FIXED on laptop copy)
--------------------------------------------------------------------------------
SYMPTOM:    /tmp/mcq_sender_probe_errors.log = 22,209 lines, ALL
            `NameError("name 'n' is not defined")` — one per RTP packet.
ROOT CAUSE: The 584-line cv2+x264 laptop copy of gst_jetson_rtp_wan.py
            (19:20) had `if self.sent_pkts % 30 < n:` where `n` is undefined
            (the loop uses `for ni, nal in enumerate(nals)`). The try/except
            in on_rtp_probe caught it and kept the process alive, but the
            exception fired BEFORE `self.rtp_ts += self.rtp_ts_step`, so
            rtp_ts never advanced -> every frame sent with RTP timestamp 0
            -> rtph264depay on the RTX merges all frames into one AU (the
            "1 frame decoded / frames_rx 0" symptom).
RESOLUTION: FIXED on the laptop copy: `% 30 == 0` (matches the older deployed
            sender, which was correct). py_compile + unit test pass. The
            deployed Jetson sender (17:25, 411 lines, v4l2src/NVENC-era) did
            NOT have this bug — the newer laptop copy must be redeployed.
STATUS:     FIXED (laptop copy; redeploy to Jetson next lab session)

================================================================================
KEY LESSON
================================================================================
WebRTC on the Jetson's GStreamer 1.14.5/libnice 0.1.14 cannot gather srflx
candidates, so it cannot traverse the phone-hotspot CGNAT. The reliable WAN
transport for McQueen is raw RTP-over-direct-NAT-punched-UDP, using the same
proven rendezvous as the control path. Everything else in this log is
operational friction, not architecture. Second lesson: the Jetson's old
GStreamer/PyGObject stack is stricter than the RTX's — buffer mapping must be
released properly (copy before unmap) and pad probes must be exception-proof.
Third lesson: confirm BOTH username and password when taking over hardware.
Fourth lesson (added at lab-exit pull, 2026-08-13): pulled evidence found a
sender bug (F1: `% 30 < n` NameError preventing rtp_ts advancement) and an
operational RTX python mismatch (F2). Full machine snapshots + logs are in
`docs/evidence/2026-08-13-lab-pull/` with manifest README.
