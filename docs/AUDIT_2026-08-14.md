     a lost META datagram no longer blocks valid frame delivery (counts as `assoc_miss`).
   - **Fix 2** — bounded jitter buffer `rtpjitterbuffer latency=50 drop-on-latency=true`
     (50 ms budget, no retransmission; late frames dropped by design).
   - **Fix 3** — bitrate from measurement, not guess: `--bitrate-kbps` arg + live
     `achieved=kbps` print; 150–400 kbps found as the sweet spots (old hardcoded 2500
     saturated the hotspot uplink → 709 ms p50).
2. **Full loop proven on a better network** — loss essentially ZERO (frames ~99.5%,

   better network (was 50–70% frame loss before). Latency p50 dropped 391 ms → ~160 ms
   at 30 fps @ 400 kbps.
3. **Approved 4-part plan COMPLETE** (all hardware-verified):
   - **Cleanup** — round 1 (old WAN scripts) + round 2 FULL SWEEP on both machines
     (git bundles, stale pids, old logs, install artifacts, `__pycache__`). Keep-list
     verified intact; nothing non-McQueen touched (DECISION 014).
   - **Save-latency test** — `--save-frames` (opt-in, default off) on the receiver:
     JPEG every frame + `meta.csv` (`frame_id`, `capture_mono_ns`, `recv_mono_ns`,
     `save_mono_ns`), async writer (never blocks the control path). recv→decode→save
     p50 1.14 ms / p95 1.54 ms; 5,277 saved / 5,270 assoc ≈ 100%, 0 dropped;
     completeness vs received 90.8% (lost-META frames not saved by design).
   - **FPS ladder + RTT probe** — same network, 150 kbps cap, ping probe during every
     run: 10→677 ms, 15→478 ms, 30→277 ms loop p50, link healthy every run (RTT
     p50 ~46 ms) → sparse-traffic penalty CONFIRMED, NOT the link. 30 fps is the winner.
     True 20 fps is impossible from a 30 fps camera (rates are 30/N).
   - **25 ms jitter buffer** at 30 fps — loop p50 281.9 ms vs 50 ms's 276.8 ms
     (statistically identical) → jitter buffer was never the latency driver; ~280 ms is
     wire/RTT. 21,400 frames saved, 0 dropped.
